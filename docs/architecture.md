# Architecture

`HarnessShell.xcodeproj` is a small, checked-in native Xcode project with a shared scheme. Xcode is the authority for build settings and dependencies; there is no generation step.

- `HarnessShell/ReadingEngine.swift`: value models, versioned content loading and validation (including daily extras, three scores, distinct area lines and question-position meanings), Gregorian local date keys and a stable SHA-256 daily draw. The engine has no UI, store, clock or random state. Pick position is saved but excluded from card selection.
- `HarnessShell/QuestionReading.swift`: pure question-edit limits, question/named-person spread selection and composition, including the optional relationship-status lens for ordinary Relationship questions and the bundled crisis-content model. The crisis rule normalises case, accents, apostrophes, punctuation and whitespace, then matches whole phrases from the finite approved list; it cannot assess meaning or reliably recognise every crisis. Composition also rejects matching questions and named-person context notes. A `NamedPerson` value holds a name, one of six relations and optional context; its presence gives a snapshot or draft the distinct `namedPerson` reading type. `ReadingType` supplies the three permitted positions. Earlier snapshots without person details remain question readings. Named-person composition requires Relationship and complete details, uses the dedicated position meanings, mentions the supplied name and always uses the neutral Relationship lens instead of the user's saved romantic status. Each pick consumes the injected bounded random source twice, selecting a remaining card and its orientation. The three position meanings, area lens and deterministically selected reflection become an immutable `QuestionReading` snapshot.
- `HarnessShell/DrawStore.swift`: SwiftData installation identity, Welcome completion, immutable daily and question-reading snapshots, one current question or spread draft, a relationship preference whose presence records that the prompt was answered or skipped, and a separate area-visibility preference. Visibility is never applied to saved-reading queries. Moving from a question draft to a spread and saving a reading clear the superseded draft in the same database transaction. New identities explicitly save Welcome as incomplete; an identity created before Welcome existed has no value and is treated as complete. A saved draw contains its card, both meanings with their extras, scores, area lines and question-position meanings, orientation, position and content version, so future content edits cannot rewrite it. Pre-full-Today snapshots decode with absent daily fields and are not backfilled. A question reading also carries optional response and note fields; absent fields decode as empty for earlier snapshots. Annotation edits read the saved snapshot and update only those fields. Successful reading edits and deletions advance History's revision; failures roll back before the screen, History or Ask cache changes. Deletion removes the stored row and returns the remaining latest readings per area. CloudKit is explicitly disabled.
- `HarnessShell/History.swift`: pure combined-history ordering/filtering and Gregorian month arithmetic on saved date keys. `HistoryScreen.swift` reads snapshots once on entry and on the store’s observed save/deletion revision, keeps the complete combined row list instantiated, and reuses Today/Reading for archive details. Read errors remain distinct from empty results. Saved timestamps sort newest first. New daily snapshots include an optional creation time; older JSON snapshots decode without it and use the start of their unchanged saved date for ordering. Equal timestamps put readings first, then use identifier tie-breaking.
- `HarnessShell/CardIdentity.swift`: the 78-card artwork catalogue (22 unsuited Majors, four suits of 14 Minors); existing reading snapshots expose the same metadata without changing storage or draw ordering. The Major Arcana interpretations are complete as a first draft; Minor Arcana expansion remains #25–#26.
- `HarnessShell/CardFaceProof.swift`: Debug-only real-app gallery and size proof, launched explicitly by UI tests.
- `HarnessShell/DesignSystem.swift`: all colour, typography, shape and spacing roles; background grain, card back/front, fan and action components. Font roles scale with Dynamic Type.
- `HarnessShell/AppSession.swift`: the sole launch composition point creates the clock, random seed, spread random source, content library and store. An observable session routes Welcome, Draw, Reveal, Today, History and the Ask flow. The clock reads the current device time zone each time; the app shell refreshes on significant-time/time-zone notifications and foreground activation. A changed date resets the daily ritual or restores that date's immutable snapshot. It saves the question and area after each composer edit, then saves the question, area, picks and composer/pick return state after submission. Ask resumes that draft without replacing the daily launch rule. Back to the composer keeps drawn cards locked; Back to Ask deletes the draft. A crisis match at submission opens support before the pick, disables draft persistence, clears in-memory question/picks and removes both saved draft types. Removal failure keeps support available with an honest retry state; a matching draft restored after interruption opens support and retries removal. Date refresh leaves support in place while updating the daily destination. It loads the latest saved reading per area for Ask and never recomposes it. A reading is composed once and saved before its screen opens; save retries reuse that snapshot. Reveal follows a successful save; a relaunch after saving routes to Today even if it was interrupted during Reveal.
- `HarnessShell/ContentView.swift`: Welcome, the daily screens and three-tab shell; `AskScreens.swift` contains Ask, composer, named-person form, pick, reading and support. `SettingsScreen.swift` contains Settings and its relationship, disclaimer and privacy pages, reached through the shell without disturbing the current daily snapshot. The session saves visibility before updating the interface; the engine rejects hiding the last area. Neither creates a store or owns reading rules. `HarnessShellApp.swift` owns startup and recoverable open failures. Welcome remains until its completion is saved, then hands off through the launch routing (Draw, or Today once today's card is drawn); a read failure there shows the open-failure screen, whose retry routes past Welcome.
- `HarnessShell/MorningReminder.swift`: the Apple UserNotifications boundary requests permission only after an explicit invitation or Settings opt-in and schedules one stable-identifier repeating calendar notification at 08:00, without a fixed date or time zone. SwiftData stores the first-draw date, invitation answer and reminder preference separately from saved readings. Saving the first draw and its invitation date is one transaction; pre-existing stores derive the date from their earliest draw. The pure `ReminderPreference` rule expires the invitation permanently on leaving that date. AppSession reconciles permission and scheduling on launch/foreground without prompting; cancelled preferences are saved before cancellation, and an enable-save failure cancels the newly scheduled request. Debug test fixtures simulate only the platform boundary and expose the actual constructed request's fields through title accessibility values, never in ordinary launches.
- `HarnessShell/DataExport.swift`: a pure engine formatter writes original saved daily and question-reading content as UTF-8 text, including notes and responses. A temporary file goes to the native share sheet; Copy reads the same file. It is removed on dismissal, before a later export/deletion and on launch after an interrupted share. Delete-all stages every stored model in one context save with rollback on failure; only success clears session caches and cancels local notification requests. Welcome remains without an identity until the user starts again (or the next app launch creates a fresh first-open identity).
- `HarnessShell/ShareImage.swift`: renders a naturally sized SwiftUI document from the saved daily or question-reading snapshot at a fixed portable width. The resulting in-memory image is passed to `UIActivityViewController`; no file, store mutation or network request is needed. Cancellation leaves the presenting screen intact.
- `HarnessShell/Resources/`: the versioned draft JSON library containing all 22 Major Arcana and original OFL variable fonts/licences. Card faces are drawn in SwiftUI using suit and rank in a small geometric grammar.
- `HarnessShellTests/`: engine tests for deterministic results, positions, dates, content completeness and snapshot encoding, plus actual UIFont registration checks.
- `HarnessShellUITests/`: real-app flow, independently tappable positions, selection changes and disk relaunch/seed preservation; reusable strict all-category accessibility audits at overlapping scroll stops and retained reference-named screenshots. Geometry checks read the actual safe area through an empty marker exposed only in Debug test mode; every deferred contrast element must be audited fully visible at a later stop. A fully visible native contrast flag can be dismissed only after its own image measures at least 4.5:1; kept records contain the identifier, label, image and ratio, and synthetic pairs check the measurement. Per-screen exposed-label checks supplement rather than replace the native audit. Test launch-argument parsing is compiled only in Debug.
- `scripts/harness`: location-aware shell entry point. `scripts/harness.py` orchestrates Apple executables using argument arrays and captures exit status without a pipeline masking it.
- `tests/`: black-box command-contract tests in disposable paths containing spaces under `.harness/`. Fake tools exercise the wrapper's decisions and failures. Their fake attachment bytes are never real iOS evidence.

The runner uses a distinct `.harness/runs/<timestamp>-<command>-<uuid>/` for every run. It never reuses a result bundle path. `metadata.json` records the selected developer directory, Xcode version, device and runtime; `commands.jsonl` records exact argument vectors. Test counts come from `xcresulttool`, not log-string matching or inferred test source contents. Raw logs and bundles remain available after failure. Test evidence export is attempted even when `xcodebuild` fails, while preserving its original failure code.

`xcresulttool export attachments` supplies `attachments/manifest.json`. The runner removes Xcode's trailing index/UUID from each image's suggested name and copies it into `screenshots/` under its test-assigned name. Unknown naming formats, missing payloads and duplicate screenshot names fail verification instead of guessing or overwriting evidence. `design-comparison.html` pairs captures with a snapshot of `docs/design-reference/`; coverage and variant paths are also recorded in both run summaries. Only exact, unsuffixed screen names satisfy coverage. See the [naming and final-pass contract](../README.md#screenshot-names-and-design-comparison).

A passed `doctor` proves tools and an available device were discovered; only actual builds establish project/toolchain compatibility. A passed `build` proves compilation. A passed `test`/`check` additionally requires test counts and attachment export. Visual inspection and the independent Codex exercise remain human/agent review steps, recorded separately. The runner does not inspect prose to claim an agent followed instructions.

The four parts are folders/files in the same app target, not separate packages. There is no speculative AI/service abstraction. The current engine draws from the bundled 22 Major Arcana; Minor Arcana interpretations belong to #25–#26. The resource retains its original `starter-cards.json` filename to avoid unrelated project-file changes. Issue #24 appends the missing Majors after the original six and increments the content version; the larger draw pool changes future unsaved results. The repeat window includes every stored draw on or after the Gregorian date key fourteen days before today, irrespective of orientation. This includes today's key and later keys reached before westward travel. The original hash input stays unchanged for attempt zero; retries append `\0retry:1`, `\0retry:2` and `\0retry:3`. The first fresh candidate wins, or the third retry is accepted even if repeated, as the spec requires. Tests use a synthetic 78-card library for a two-year repeat-free run and separately prove this bounded fallback. Do not change the versioned hashing input or library ordering casually: that would change future unsaved daily results. Previously saved snapshots always win.
